# Continuidade do supervisor

Componente opcional, independente do Worker. `core.mts` é a máquina de estados; `rpc.mts` consulta o app-server oficial sem inferência; `run.mts` reconcilia quota, dependências e respostas; `platform.ps1` serializa por mutex e integra o Agendador; `install.ps1` instala por conversa. `scripts/sync-src.mjs` transpila TypeScript pelo Node e espelha somente a seleção positiva em `src/supervisor/`. Runtime testado: Node 22.21, PowerShell 5.1/7, Windows 11; mínimo técnico Node 22.13 para o gerador, 22 para os artefatos gerados com SQLite.

## Contrato SR-001, versão 1

Cobertura é por conversa instalada, não por presença do Worker nem por conta. Repetir `install.ps1 -ThreadId <ID confirmado> -RepoPath <raiz confirmada>` registra outra conversa de forma independente, com diretório, mutex e tarefa próprios. Instalar uma conversa não monitora automaticamente as demais. O instalador imprime explicitamente o ID coberto; uma instalação só deve ser apresentada como global se houver mecanismo global efetivamente instalado.

Recuperação tardia: o último turno da conversa registrada com `status=failed` e código estruturado `usageLimitExceeded` produz evento exclusivo pelo ID do turno. Não se interpreta texto de mensagem nem se presume horário pela UI. Se a telemetria atual já comprova cota restaurada, a recuperação ocorre na próxima passagem, com `RECOVERED_QUOTA_CATCH_UP`; se ainda limitada, agenda pelo reset verificável +60s. Isso não afirma cumprimento retroativo de um horário perdido. Evento já pendente é reaproveitado quando cobre o incidente; um envio posterior ao incidente impede outro. Antes do envio, inclusive após preparar dependências, turno mais recente cancela a recuperação obsoleta com `RESOLVED_EXTERNALLY` (sem afirmar resposta do supervisor). Erros de outra classe e conversas não cadastradas não são retomados.

Gatilho: autorização explícita por chat, saldo oficial <=10%. Entrada privada `config.json` schema 1, gerada pelo instalador. Saída `status.json`, `events/<sha256>.json`, tarefas por thread/ciclo. Efeitos: iniciar componentes instalados, restaurar arquivos ausentes de cópia íntegra, reparar registro MCP, enviar somente `continue`. Não altera modelo/esforço, não inicia inferência local, não reinicia jobs, não armazena credenciais, não consome créditos de reset.

Estado: SCHEDULED → SENDING → SENT → RECEIVED → COMPLETED; RETRY, WAITING_QUOTA, SEND_AMBIGUOUS, RESPONSE_ERROR, AMBIGUOUS_RESPONSE e RESPONSE_OBSERVED_UNCORRELATED preservam impedimentos. `COMPLETED` exige resposta final de turno sem erro e identidade confirmada. O CLI atual emite ID da fila, distinto do ID recebido. `receipts.mts` observa somente leitura a fila durante o envio, liga seu ID ao clientId e confronta o clientId recebido. Se a fila for consumida antes da observação, ou o schema não for compatível, não inventa correlação. A projeção local de histórico fornece estado/primeira mensagem/resposta final sem carregar raciocínio; é necessária porque um app-server separado pode apresentar turno ativo como interrompido. `continue` manual concorrente não pode ser atribuído silenciosamente à automação.

Com clientId comprovado, cada passagem consulta diretamente a projeção persistida antes de autenticação/rede, sem aguardar backoff nem limitar a busca aos turnos recentes. Conclusão anterior pode ser confirmada mesmo offline; isso não concede novo envio. Repetição de clientId em múltiplos turnos é ambiguidade, não sucesso. A primeira mensagem e a resposta final são selecionadas pelos IDs canônicos da projeção, sem leitura do histórico privado de ferramentas/raciocínio.

O enum interno `final_answer` é traduzido para `final` somente no item explicitamente apontado por `final_agent_item_id`. Falha ao consultar confirmação é `CONFIRMATION_RETRY`, sem novo envio; `sendAttempts` e `recoveryAttempts` distinguem essas operações. `attempts` legado conta operações de ambos os tipos e não comprova múltiplas mensagens. Diagnósticos históricos permanecem auditáveis mesmo quando a resposta posterior é confirmada.

Idempotência: `cycles.json` mantém a identidade do episódio por conta/chat/diretório/janela. Refinamento de resetsAt atualiza o agendamento do evento ainda não enviado, sem criar outro envio. Nova janela exige evidência de restauração/passagem do ciclo; não basta o timestamp variar. Persistência precede envio; mutex nomeado do SO, inclusive após abandono; `IgnoreNew` nas tarefas. Não há retry de envio ambíguo. Retry antes do envio: 30s a 15min. Consulta normal: 2min, sem inferência. RPC: 30s, recuperação auxiliar: 90s, tarefa: 10min (limites técnicos de infraestrutura, não do Worker). Eventos já recebidos são reconciliados sem reenvio. Ausência de resposta não é sucesso.

Configuração: `ThreadId`, `RepoPath` obrigatórios; `Target`, `CodexHome`/`CODEX_HOME`, `WorkerHome`/`LOCAL_WORKER_HOME`, `NodeExe`, `CodexExe`, `OllamaExe`, `ScanMinutes` opcionais. Paths descobertos no ambiente real ou parametrizados. `config.json`: executáveis, AppUserModelID, hash da identidade autenticada, tarefa/mutex, repo/chat, endpoint Ollama e intervalo. Sem senhas/tokens. `core.mts:POLICY_S8R`: limiar, atraso e backoff; mudar exige validar contrato humano. Configuração privada não é distribuída.

Recuperação: Desktop pelo AppUserModelID instalado; Ollama por `serve`; Worker ausente por arquivos individuais com SHA-256 e `npm ci --ignore-scripts`; MCP e monitor pelos próprios adaptadores existentes. Arquivos existentes não são sobrescritos nessa recuperação. Modelo ausente/corrompido, Desktop desinstalado, binário Node ausente, mudança de conta ou login que exija pessoa recebem diagnóstico. Não há armazenamento de senha, instalação furtiva ou contorno de MFA. Atualizar a instalação renova a cópia privada de recuperação.

Persistência sobrevive a reboot. Tarefas usam token interativo do próprio usuário, sem senha: antes do logon não há Desktop autenticado; `StartWhenAvailable` e gatilho de logon recuperam o atraso. Suspensão permite WakeToRun conforme política/energia; desligamento não. Horário configurado = resetsAt+60s; latência do SO, rede e prontidão impedem garantia de execução/resposta exatamente naquele segundo. A consulta discreta também não detecta instantaneamente uma queda de cota entre duas amostras.

Logs contêm somente estado, IDs, recibo técnico do envio e hashes de resposta, sem texto privado. Cada evento é atualizado no próprio arquivo; não há log crescente por retry. Eventos COMPLETED são removidos após 90 dias e desregistro da tarefa; eventos pendentes permanecem para não perder retomada. Limite de 512 eventos interrompe novas detecções com diagnóstico e mantém reconciliação dos já existentes. Telemetria antiga é recusada, impedindo recriar ciclo expirado após limpeza. Volume por evento é limitado por metadados, nunca por histórico completo do chat.

Operação/remoção: desabilitar/remover somente tarefas com o prefixo registrado no config desta instalação interrompe monitoramento, não Worker/chat. Preservar events/config para reinstalação idempotente. Não apagar o diretório do Worker. Hooks/callbacks extras: nenhum. Teste: `node supervisor/test-core.mts`; `run.mjs --probe` valida autenticação/identidade/Worker/monitor; `platform.ps1 -Action TestEvent -Config <arquivo>` agenda UMA mensagem real autorizada 60s depois, identificada como teste, sem simular quota. Exit 0 = passagem de monitor concluída, não conclusão da conversa; exit 3 = impedimento recuperável/pré-condição; falha de PowerShell retorna erro. Este componente não é requisito do Worker.
