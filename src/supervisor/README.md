# Continuidade do supervisor

Componente opcional, independente do Worker. `core.mts` é a máquina de estados; `rpc.mts` consulta o app-server oficial sem inferência; `run.mts` reconcilia quota, dependências e respostas; `platform.ps1` serializa por mutex e integra o Agendador; `install.ps1` instala por conversa. `scripts/sync-src.mjs` transpila TypeScript pelo Node e espelha somente a seleção positiva em `src/supervisor/`. Runtime testado: Node 22.21, PowerShell 5.1/7, Windows 11; mínimo técnico Node 22.13 para o gerador, 22 para os artefatos gerados com SQLite.


## Pausa e intenção humana — U6C

Instalação nova/legada começa pausada. Antes de autorizar continuidade de trabalho pendente, abra manualmente o Desktop e use os comandos abaixo no PowerShell. `<destino>` é o diretório efetivamente informado pelo instalador, nunca um path presumido:

```powershell
$DestinoU6C = Read-Host 'Diretório instalado desta conversa'
$ConfigU6C = Join-Path $DestinoU6C 'config.json'
& (Join-Path $DestinoU6C 'platform.ps1') -Action Pause -Config $ConfigU6C
# Somente quando quiser autorizar novamente a continuidade nesta sessão aberta:
& (Join-Path $DestinoU6C 'platform.ps1') -Action Resume -Config $ConfigU6C
```

`Pause` é persistente, sem depender de telemetria/serviços. `Resume` exige Desktop aberto, gera autorização nova por conversa e não dispara `continue` imediatamente. Reautoriza somente evento não enviado com o mesmo turno ainda falho por quota; eventos legados sem origem verificável e envios ambíguos não são repetidos. Quota baixa em conversa concluída não gera trabalho. A tarefa periódica faz observação silenciosa, nunca rearma após boot. `continuity.json` registra schema/mode/reason/session/generation/authorizedAt; bootId e PID+início da instância são identidades técnicas, sem credenciais. Ausência de janela, troca da instância/sessão, pausa explícita ou turno interrompido/substituído bloqueiam envio/ativação; `status.json` e eventos mostram PAUSED_USER e motivo. A integração não tem telemetria autoritativa de intenção para todo crash/fechamento: na dúvida pausa. Erros transitórios de rede/prontidão continuam recuperáveis enquanto autorização válida.

`continuity.mts/.mjs/.ps1` são derivados da fonte comum `localworker/continuity.mts/.ps1` pelo gerador; não editar cópias. Paths: SystemRoot/WINDIR fornecidos pelo SO; executáveis/destinos já são parâmetros da instalação. Observação Win32 foi implementada; outras plataformas retornam indisponibilidade e não fazem retomada. Não se afirma instalador Linux. Nada abre navegador/UI de monitor automaticamente no boot. Uma mensagem já aceita na fila nativa pode executar quando o usuário abrir o app: o CLI inspecionado não fornece cancelamento. Não se altera a fila por SQLite nem se promete revogação de envio já aceito. As guardas impedem novos envios e ativações; resultados e recibos permanecem.

## Contrato SR-001, versão 1

C9R conserva a autorização diante de falha estruturada de quota (`failed` + `error.codexErrorInfo=usageLimitExceeded`), usando a mesma classificação do callback. Isso não vale para `interrupted`, erros genéricos/texto livre, cancelamento ou sessão/instância diferente. O status `PAUSED_USER` de pausa explícita permanece persistente; instalar/atualizar não executa Resume. Recebimento e resposta real continuam obrigatórios para COMPLETED. A cobertura continua por conversa instalada/autorizada, não global por inferência.

`serverOverloaded`, também comprovado no runtime/schema, é causa temporária distinta: `STRUCTURED_SERVICE_BACKOFF` registra causa, incidente, tentativa e espera. Inicial30s; tentativas de serviço ainda não confirmadas na mesma autorização elevam a espera até15min. Não há API presumida de prontidão do serviço: cada envio é continuação real do pedido pendente, não consulta paga de status. Um incidente cria no máximo um evento; fila/reserva/intenção continuam prevalecendo. Quota100 bloqueia também essa tentativa até a restauração verificável. Recebimento de erro não equivale a conclusão e não autoriza repetir mensagem aceita/ambígua; somente novo incidente comprovado pode gerar nova continuação.

Arbitragem C9R: antes do envio, o mutex canônico protege consulta aos eventos persistidos da mesma conta/conversa/repositório/origem. Envio já iniciado por outro evento, inclusive ambíguo, impede nova reserva daquela origem (`ORIGIN_DISPATCH_ALREADY_RESERVED`); isso não declara o trabalho concluído. Qualquer entrada já pendente naquele chat tem precedência: `WAITING_QUEUED_INPUT`, checagem local gratuita e sem ativação/reenvio. Fila indisponível gera diagnóstico/retry, nunca autorização presumida. Nenhum texto de mensagens é lido nessa arbitragem.

O CLI configurado é preservado enquanto existir como arquivo executável regular. Quando uma atualização remove seu diretório versionado, `rpc.mts` reutiliza `codexCommand` do runtime instalado, com descoberta por configuração, PATH e instalação Desktop; se o Worker estiver ausente, usa a cópia íntegra de recuperação. O caminho resolvido vale para todas as operações daquela passagem, inclusive MCP e envio. O instalador aplica a mesma descoberta antes de validar paths. Ausência de alternativa válida gera `CODEX_CLI_UNAVAILABLE`, sem novo envio; teste dirigido: `node supervisor/test-rpc.mts`.

Cobertura é por conversa instalada, não por presença do Worker nem por conta. Repetir `install.ps1 -ThreadId <ID confirmado> -RepoPath <raiz confirmada>` registra outra conversa de forma independente, com diretório, mutex e tarefa próprios. Instalar uma conversa não monitora automaticamente as demais. O instalador imprime explicitamente o ID coberto; uma instalação só deve ser apresentada como global se houver mecanismo global efetivamente instalado.

Recuperação tardia: o último turno da conversa registrada com `status=failed` e código estruturado `usageLimitExceeded` produz evento exclusivo pelo ID do turno. Não se interpreta texto de mensagem nem se presume horário pela UI. Se a autorização U6C continua válida e a telemetria atual já comprova cota restaurada, a recuperação ocorre na próxima passagem, com `RECOVERED_QUOTA_CATCH_UP`; se ainda limitada, agenda pelo reset verificável +60s. Isso não afirma cumprimento retroativo de um horário perdido. Evento já pendente é reaproveitado quando cobre o incidente; um envio posterior ao incidente impede outro. Antes do envio, inclusive após preparar dependências, turno mais recente cancela a recuperação obsoleta com `RESOLVED_EXTERNALLY` (sem afirmar resposta do supervisor). Erros de outra classe e conversas não cadastradas não são retomados.

Gatilho: autorização explícita por chat, saldo oficial <=10%. Entrada privada `config.json` schema 1, gerada pelo instalador. Saída `status.json`, `events/<sha256>.json`, tarefas por thread/ciclo. Efeitos sob autorização U6C: iniciar serviços instalados (nunca Desktop fechado), restaurar arquivos ausentes de cópia íntegra, reparar registro MCP, enviar somente `continue`. Não altera modelo/esforço, não inicia inferência local, não reinicia jobs, não armazena credenciais, não consome créditos de reset.

Estado: PAUSED_USER preserva impedimento/intenção, sem envio ou ativação. SCHEDULED → SENDING → SENT → RECEIVED → COMPLETED; RETRY, WAITING_QUOTA, SEND_AMBIGUOUS, RESPONSE_ERROR, AMBIGUOUS_RESPONSE e RESPONSE_OBSERVED_UNCORRELATED preservam impedimentos. `COMPLETED` exige resposta final de turno sem erro e identidade confirmada. O CLI atual emite ID da fila, distinto do ID recebido. `receipts.mts` observa somente leitura a fila durante o envio, liga seu ID ao clientId e confronta o clientId recebido. Se a fila for consumida antes da observação, ou o schema não for compatível, não inventa correlação. A projeção local de histórico fornece estado/primeira mensagem/resposta final sem carregar raciocínio; é necessária porque um app-server separado pode apresentar turno ativo como interrompido. `continue` manual concorrente não pode ser atribuído silenciosamente à automação.

Com clientId comprovado, cada passagem consulta diretamente a projeção persistida antes de autenticação/rede, sem aguardar backoff nem limitar a busca aos turnos recentes. Conclusão anterior pode ser confirmada mesmo offline; isso não concede novo envio. Repetição de clientId em múltiplos turnos é ambiguidade, não sucesso. A primeira mensagem e a resposta final são selecionadas pelos IDs canônicos da projeção, sem leitura do histórico privado de ferramentas/raciocínio.

O enum interno `final_answer` é traduzido para `final` somente no item explicitamente apontado por `final_agent_item_id`. Falha ao consultar confirmação é `CONFIRMATION_RETRY`, sem novo envio; `sendAttempts` e `recoveryAttempts` distinguem essas operações. `attempts` legado conta operações de ambos os tipos e não comprova múltiplas mensagens. Diagnósticos históricos permanecem auditáveis mesmo quando a resposta posterior é confirmada.

Idempotência: `cycles.json` mantém a identidade do episódio por conta/chat/diretório/janela. Refinamento de resetsAt atualiza o agendamento do evento ainda não enviado, sem criar outro envio. Nova janela exige evidência de restauração/passagem do ciclo; não basta o timestamp variar. Persistência precede envio; mutex nomeado do SO, inclusive após abandono; `IgnoreNew` nas tarefas. Não há retry de envio ambíguo. Retry antes do envio: 30s a 15min. Consulta normal: 2min, sem inferência. RPC: 30s, recuperação auxiliar: 90s, tarefa: 10min (limites técnicos de infraestrutura, não do Worker). Eventos já recebidos são reconciliados sem reenvio. Ausência de resposta não é sucesso.

Configuração: `ThreadId`, `RepoPath` obrigatórios; `Target`, `CodexHome`/`CODEX_HOME`, `WorkerHome`/`LOCAL_WORKER_HOME`, `NodeExe`, `CodexExe`, `OllamaExe`, `ScanMinutes` opcionais. Paths descobertos no ambiente real ou parametrizados. `config.json`: executáveis, AppUserModelID, hash da identidade autenticada, tarefa/mutex, repo/chat, endpoint Ollama e intervalo. Sem senhas/tokens. `core.mts:POLICY_S8R`: limiar, atraso e backoff; mudar exige validar contrato humano. Configuração privada não é distribuída.

Recuperação autorizada: Desktop deve estar aberto pelo humano; Ollama por `serve`; Worker ausente por arquivos individuais com SHA-256 e `npm ci --ignore-scripts`; MCP e monitor pelos próprios adaptadores existentes. Arquivos existentes não são sobrescritos nessa recuperação. Modelo ausente/corrompido, Desktop desinstalado, binário Node ausente, mudança de conta ou login que exija pessoa recebem diagnóstico. Não há armazenamento de senha, instalação furtiva ou contorno de MFA. Atualizar a instalação renova a cópia privada de recuperação.

Persistência sobrevive a reboot para preservar dados, sem retomar conversas. Tarefas usam token interativo do próprio usuário, sem senha, sem gatilho de logon/boot, StartWhenAvailable ou WakeToRun. A autorização anterior é invalidada por troca de sessão do SO ou instância do Desktop; reaparecimento do aplicativo não rearma eventos. Horário configurado = resetsAt+60s; latência do SO, rede e prontidão impedem garantia de execução/resposta exatamente naquele segundo. A consulta discreta também não detecta instantaneamente uma queda de cota entre duas amostras.

Após enviar, se o ID exato da fila ainda contiver o clientId esperado no thread autorizado, a recuperação ativa `codex://threads/<ThreadId>` pelo protocolo registrado do aplicativo. A rota foi verificada no Desktop instalado; não contém prompt e não envia outra mensagem. Registro de protocolo ausente gera diagnóstico, sem simular navegação. PID e início do processo identificam a instância do Desktop: uma ativação por evento/instância, somente dentro da autorização U6C vigente, sem mudanças periódicas de tela na mesma instância. Reboot/reabertura exigem autorização explícita nova. A ativação pode selecionar o chat original na UI; não cria console transitório. Fila consumida, clientId incorreto, outro thread ou resposta já recebida não autorizam ativação. Ainda se exige resposta final correlacionada para `COMPLETED`.

Logs contêm somente estado, IDs, recibo técnico do envio e hashes de resposta, sem texto privado. Cada evento é atualizado no próprio arquivo; não há log crescente por retry. Eventos COMPLETED/RESOLVED_EXTERNALLY e pausados sem envio são removidos após 90 dias e desregistro da tarefa; eventos enviados/ambíguos pendentes permanecem para não perder rastreabilidade. Limite de 512 eventos interrompe novas detecções com diagnóstico e mantém reconciliação dos já existentes. Telemetria antiga é recusada, impedindo recriar ciclo expirado após limpeza. Volume por evento é limitado por metadados, nunca por histórico completo do chat.

Operação/remoção: desabilitar/remover somente tarefas com o prefixo registrado no config desta instalação interrompe monitoramento, não Worker/chat. Preservar events/config para reinstalação idempotente. Não apagar o diretório do Worker. Hooks/callbacks extras: nenhum. Teste: `node supervisor/test-core.mts`; `run.mjs --probe` valida autenticação/identidade/Worker/monitor; `platform.ps1 -Action TestEvent -Config <arquivo>` agenda UMA mensagem real autorizada 60s depois, identificada como teste, sem simular quota. Exit 0 = passagem de monitor concluída, não conclusão da conversa; exit 3 = impedimento recuperável/pré-condição; falha de PowerShell retorna erro. Este componente não é requisito do Worker.
